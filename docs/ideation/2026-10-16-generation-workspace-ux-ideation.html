Grounding Context

Codebase Context. mlx-create is pre-implementation. docs/HLD.md (decisions D1-D20, upstream engine requests F1, F3-F5) and docs/lld/engine.md are the evidence layer. Every citation below is a docs line, not code.

  • Workspace as specified. D18 / §10: canvas-first window with toolbar, canvas, filmstrip with queue placeholders, prompt bar (Enhance, settings popover, ×N batch, ⌘↩) and a LoRA row. D13: batch count, seed controls, persistent queue and live step previews in v1; X/Y, wildcards and styles out. D14: no sampler picker. §8.2: app-owned SQLite queue, one engine job at a time, a job expands into N separate engine requests, with seed policies random, fixed, increment and reuse-from-image.
  • Controls come from data. §8.3-8.4: the family capability record drives every control, so the UI never shows a knob the engine would reject. Capabilities arrive in the signed catalog.
  • Enhance. §8.8: non-blocking LLM rewrite shown as an inline diff (accept / revert / regenerate). On the 16 GB tier the LLM unloads afterward and the diffusion model re-warms (HLD:431).
  • Metadata. D12 / §8.9: A1111 parameters chunk plus an mlx-create iTXt JSON chunk; drop-PNG restores settings.

Gaps the docs leave open (these are where most survivors come from):

  • Fast / Balanced / Quality presets have no values (HLD:307). No queue ETA formula exists, and pause and retry semantics are undefined (HLD:266, :270; engine.md:276).
  • Image step previews depend on upstream F1 (HLD:215, :649), yet D13 lists previews as a v1 tool.
  • No compare view, no lineage field on IMAGE (HLD:489-506), no variation UI (img2img strength is v1.x, HLD:622).
  • D18 is the only decision whose rationale cell is empty (HLD:61). PROMPT_HISTORY appears in the ER diagram (HLD:462) but has no entity definition.
  • Entitlement gates (batch cap, queue depth) have no UI (HLD:449).

Hard bounds from AGENTS.md: no content filtering, no in-app inference, stock upstream engine (engine changes only as upstream PRs like F1), everything on-device, on 16 GB the enhancer LLM and diffusion model are never co-resident, and out of scope are sampler pickers, tags/ratings/smart collections, SDXL/SD1.5 engines and ControlNet.

External context (web research, 2026). Invoke 6.14.0 publishes a per-family capability matrix and fails early with a reason. Tanque Studio, a Swift companion for Draw Things, expands axes into an editable render queue and keeps a config snapshot per row. Draw Things pastes a JSON config to set model, LoRA, steps and size. Mochi Diffusion users asked for same-seed sweeps, and the maintainer answered with scripting. DiffusionBee's top complaints were LoRAs that fail to load and unreliable model import. No concrete Shortcuts or Quick Look implementation was found in Draw Things, Invoke or Mochi.

Verification depth Each generating agent had a budget of 5 verification reads, shared across 6-16 ideas, so per-idea scrutiny was uneven. A separate verifier then checked the load-bearing direct: quotes against the docs and judged each idea against the meeting-test. It did not re-fetch external prior art, so external: bases are as reported by web research. The axis-3 scout wrote no dossier; ideation agents read the HLD directly for that axis.

1. Time is the workspace's currency

Axis: Waiting and queueConfidence 80%Complexity Medium
Description
One calibration table feeds three surfaces. It records seconds per step by model, resolution and LoRA-stack identity, plus measured model-load and enhancer-swap cost. The surfaces are the model chip estimate, a queue clock that shows time remaining for the whole queue with explicit reload lines, and the Fast / Balanced / Quality presets restated as a target seconds-per-image. The app picks the step count and size inside the family's curated range and shows them read-only. When consecutive jobs differ in model, LoRA stack or enhancer residency, the queue shows an offer such as "regrouping saves about 40 s". It never reorders silently.
Axis
Waiting and queue (also settles the Parameter surface presets)
Basis
direct: HLD:307 "quality presets (Fast / Balanced / Quality), max 100" with no values given. HLD:353 "every real generation records seconds-per-step by (model, resolution, LoRA count)". HLD:348 "picks the largest comfortable model whose estimated latency meets the tier target". HLD:270 "The engine already reuses an identical LoRA stack between requests". HLD:431 "Enhance unloads the LLM afterwards and re-warms the diffusion model". HLD:524 lora_count, HLD:503 duration_ms. Verified against the docs; the queue dossier confirms no ETA formula exists.
Rationale
The calibrator is already planned, but it only feeds the chip. Before F1 ships, image progress is step-only (AGENTS.md:51), so time remaining is the one "when" signal users get. Keying on stack identity rather than lora_count matches what the engine's reuse actually depends on, and changing the key after data accrues is expensive.
Downsides
The quality-versus-steps curve is model-specific and unmeasured, and turbo or distilled families have little step range, so presets collapse to one value there. The docs give no swap-time figures, so the first calibration needs catalog-seeded defaults. A "regroup" offer touches the HLD:270 no-reorder rule, and the offer wording has to stay clearly optional.

2. Failure routing by cause, with per-generation resume

Axis: Waiting and queueConfidence 80%Complexity Medium
Description
Persist status per generation, not per job. If generation 3 of ×4 fails, retry re-enqueues only the unfinished generations with their recorded seeds, so no finished render is repeated. The engine's crash class picks the response. For outOfMemory and killedBySystem, unload idle models, wait, and retry the identical request once; if it still fails, park the job as paused with a plain-language tier hint instead of marking it failed. For missingWeights, pause only the jobs that use that model. The request is never altered, so no LoRA is dropped silently.
Axis
Waiting and queue
Basis
direct: engine.md:269-271 (crash classes, with outOfMemory retryable and missingWeights not retryable until repaired). engine.md:276 "Retrying is the queue's decision. The supervisor never replays a request." HLD:266 "reorder, pause, cancel (current or queued), and retry failed jobs". HLD:486 status enum already includes paused. AGENTS.md:43 "always send an explicit seed". Verified.
Rationale
The docs hand retry to the queue but never define granularity or policy, so a naive job-level retry re-spends compute on work that finished, and the OOM hint ("Try a smaller model or fewer LoRAs") pushes the fix back onto the user. Here the policy falls out of the crash taxonomy the LLD already specifies.
Downsides
A single automatic retry on a 16 GB machine may just repeat the failure. Parked jobs need a visible state in the filmstrip. It treats the symptom, since admission control (idea 3) is what reduces how often this path runs. It depends on the pinned engine's crash signatures staying stable across bumps.

3. Admission control: only queue jobs that can run

Axis: Parameter surface and family capabilitiesConfidence 75%Complexity Medium
Description
One validator runs at enqueue. It checks size grid, step range, guidance flag, LoRA count, the safetensors key-and-shape fingerprint, and a live free-memory check against the engine's real preflight numbers rather than only the static Metal working set. A job that fails is rejected with a reason before taking a queue slot; a job that merely lacks memory is held with the gap stated ("needs about 17.6 GB free, about X now"). Engine verdicts (accepted, or "no modules matching") are remembered by LoRA SHA-256, family and engine version, and invalidated on an engine bump.
Axis
Parameter surface and family capabilities
Basis
direct: AGENTS.md:58 "Pre-check compatibility locally from the safetensors header (key names and tensor shapes, HLD §8.6). Treat the engine's 400 as the final authority." HLD:283 "Validate against FamilyRegistry capabilities". HLD:367 "Incompatible LoRAs are greyed out for the current model." HLD:342 and :347 (static working-set classification). engine.md:313 (about 14.7 GB peak, about 17.6 GB free for Krea-2 Turbo). HLD:353 (estimates invalidated on engine bump, the same pattern reused for verdicts). external: Invoke 6.14.0 fails early with a stated reason; DiffusionBee #570 lists LoRAs that fail to load among its top complaints. Verified against the docs.
Rationale
The queue is where a bad job costs the most, because it persists across relaunches and fails after the user has walked away. A fit badge computed against a static limit can say "comfortable" while the engine's preflight, which reads live memory, would refuse. One validator can serve the composer (greyed LoRAs), enqueue and pre-warm.
Downsides
Free memory moves, so a job can pass at enqueue and still fail at run; idea 2 remains necessary. Per-model fit thresholds need calibration, and the "exceeds" badge treatment is still undefined (HLD:584). Verdict memory alone is modest value. A local smoke test saw an out_of_memory refusal at low free memory, but that observation is not recorded at a cited docs line, so it is not used as a basis.

4. Review mode: cull stream with a pinned reference

Axis: Canvas and result handlingConfidence 65%Complexity Medium
Description
A ×N batch streams its results into a full-canvas review. K keeps, X discards, space advances, and the next generation is already rendering. Any earlier result can be pinned beside the incoming one, so the reference no longer disappears when the live preview takes over the canvas. Discards leave the project by default; marks are session-only so they do not become ratings. Layout and interaction only, with no engine change.
Axis
Canvas and result handling (also touches Exploration)
Basis
direct: HLD:265 "The executor expands a job into N generations, each a separate engine request". HLD:266 queue placeholders with live progress. HLD:581 "Canvas: the selected result or the live preview", so the reference is displaced. HLD:594 "Keyboard first: ⌘↩ generate, ⌘E enhance, ⌘. cancel, ⌘1/⌘2 Canvas/Gallery". HLD:35 lists ratings and favorites as non-goals. external: Mochi Diffusion #196 (users wanted same-seed side-by-side comparison). reasoned: with 8-60 s jobs the human's attention, spent during review, is the scarce resource, which is what film dailies are organized around.
Rationale
Today a batch lands in the filmstrip and the user must sort it later in a separate Gallery mode, with double-click as the only bridge (HLD:585). The docs describe no review flow at all for a canvas-first window, and no compare surface.
Downsides
"Discard leaves the project" is destructive and needs undo or a trash. Where a kept result's "keep" state lives, if marks are session-only, is a team call against the D10 no-ratings boundary. It adds a mode to the §10 layout.

5. Cross-family fan-out compare

Axis: Exploration and iterationConfidence 55%Complexity Medium
Description
One Generate sends the same prompt to several installed families. Each run uses that family's capability-driven settings and its own prompt pack, and the results land as one comparison set. The model chip becomes a multi-select. On 16 GB the runs are serial, and the queue clock from idea 1 shows the reload cost instead of hiding it.
Axis
Exploration and iteration
Basis
direct: HLD:48 D5 (FLUX.2-klein, Krea-2, Qwen-Image 2.1, Mage-Flow). HLD:300 controls driven by the capability record. HLD:602 (48 GB+ tier allows three resident models). AGENTS.md:40 "One job at a time." external: Invoke 6.14.0 publishes a per-family capability matrix. Verified: the verifier ranked this among the six strongest candidates, with the note that 16 GB fan-out is serial and must say so.
Rationale
The comparison people actually want is across families on one prompt, not one model at a time. The capability records are what make a safe fan-out possible without per-screen special cases.
Downsides
Each family needs weights on disk (roughly 5-15 GB apiece). A fair comparison is undefined when sizes differ (FLUX is fixed at 1024²). On 16 GB (one resident model) a fan-out of four families is four loads. It sits next to the D13 "no X/Y" line, so the decision log should state that a model axis is allowed.

6. Enhance receipts

Axis: Prompt authoringConfidence 60%Complexity Low
Description
Mark the trigger words that validation re-inserted as distinct spans in the inline diff. Persist the diff outcome (accepted, reverted, regenerated) and the enhancer's notes with each generation, so any image traces back to the exact prompt the user approved. Optionally keep the original prompt as a same-seed control render.
Axis
Prompt authoring
Basis
direct: HLD:424 "Trigger words are required in the output, and the JSON-schema validation re-inserts any that are missing." HLD:430 "the result is offered as a diff". HLD:408 json_schema {prompt, negative_prompt?, notes}. HLD:500-502 prompt, negative_prompt and enhanced_from are IMAGE fields, with no field for accept or revert state. HLD:432 the offline evaluation compares generations with and without enhancement. Verified; the verifier corrected the dossier, which had placed those fields on JOB.
Rationale
After a revert the prompt that produced a result is not recoverable, and users cannot see words the app added. The product's trust story for Enhance depends on it being auditable.
Downsides
Modest on its own, and its value scales with how much people use Enhance. Span provenance gets fuzzy once the user hand-edits an accepted rewrite. It needs new fields, but amends no D* decision. The K-rewrites-as-batch variant was left out because it sits too close to the D13 wildcards exclusion.

7. Explore cheap, promote the keeper

Axis: Exploration and iterationConfidence 35%Complexity High
Description
Explore with drafts at the smallest allowed size and steps. When image previews exist, use them as a stop signal: cancel a bad seed at roughly step 4-6 and let the queue move on. Promote a chosen seed to full settings as a child result. Each child records parent_image_id and a recipe_diff, so the filmstrip can read as a "what changed" chain. Two cheap experiments gate the whole idea: does a fixed seed keep its composition when size and steps change, and is composition legible at early steps?
Axis
Exploration and iteration
Basis
direct: AGENTS.md:63 (FLUX fixed at 1024², Krea multiples of 16 in [256, 2048]). engine.md:312 a 512×512 image in about 8.5 s. HLD:72, :215 and :649 (image previews depend on upstream F1). HLD:295 cancel closes the connection and the engine aborts denoise. HLD:489-506 IMAGE has no parent field. HLD:622 img2img strength is v1.x. reasoned: cancelling at 25% of steps saves about 75% of that generation's time. Both gating premises are [INFERENCE]: nothing in the docs shows that seed composition survives a size or step change, or that early steps predict the final image.
Rationale
At about 8.5 s per 512² image, exploration speed is the bottleneck, and a draft that keeps composition would multiply how many candidates a user can look at per minute. The lineage column is the one part that pays off whichever way the experiments land.
Downsides
If seed composition is unstable the idea fails outright. FLUX.2-klein is fixed at 1024², so it cannot draft, and it is the 16 GB default. Image previews depend on F1 landing upstream with no date. Run the two experiments (about a day each) before committing anything but the lineage column.
